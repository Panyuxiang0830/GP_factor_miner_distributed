## halo 三种方案（E4，未开始）

| 方案 | 对应 | 怎么做 | 状态 |
|---|---|---|---|
| 一次补齐所需历史 | 策略 A，冗余计算（`H0 ≥ max h`） | 每个 rank 多读 `h` 天的原始字段，本地把整棵树算完，不通信 | ❌ |
| 按需获取子树结果 | 策略 B，子树 halo 交换（`H0 = 0`） | 按 DAG 的 level 逐层算；每层算完后把左邻居需要的尾部 `halo_rows` 行用一次 `MPI_Sendrecv` 发过去 | ❌ |
| 冗余存储 + 按需通信 + 结果复用 | 混合（`0 < H0 < max h`） + 缓存 | 每个 rank 预留 `H0` 天历史；节点的 `h ≤ H0` 就本地补算，`h > H0` 才交换；跨层复用缓存结果 | ❌ |

说明：
- 按日期切块时，一个 rank 缺的历史只会在它的左邻居手里。所以策略 B 不会变成"到处要小数据"：每个 level 只有一次批量 Sendrecv。
- 三种方案共用同一个 `H0` 旋钮。计划先做 B，再用 `H0` 扫出 A 和混合方案。

计划的实验：
- 分别用 p = 1、2、4 和 8 个 rank 跑。
- 对每个 p，`H0` 取 0、10、30、60、89。
- 每次记录这几项：
  - 计算时间；
  - 通信时间；
  - 冗余计算的行数；
  - 显存或内存峰值；
  - 分布式结果与 p=1 是否一致。

### 2026-10-31 E5：串行算子 vs pandas

**做法**
- 数据：真实数据的 120 天 × 300 只股票小样本，132 个字段。
- 用 `python/scripts/export_reference.py values` 让 Python 原版算出 pandas 的标准答案（float64）。
- 用 `tests/test_ops_reference` 比对 C++ 的结果。
- 判定条件：每个元素满足 `|C++ − pandas| ≤ 1e-4·|pandas| + 1e-5·rms(pandas)`，并且 NaN 的位置完全一致。
- 加绝对项 `1e-5·rms`，是因为 pandas 自己有几处在 float32 下计算（pct_change、zscore 的输入），会产生舍入误差。

**用例**
- 0–47：每个算子分别用窗口 1、5、20，外加几个嵌套表达式。
- 50–89：40 个已选因子。

**结果：88 个用例，通过 86 个；约一半在舍入到 float32 后和 pandas 逐位相同。**

| 算子 | 结果 |
|---|---|
| + − × ÷ abs rank lag delta | 误差为 0 |
| mean sum std max min median（窗口 1/5/20） | 误差为 0 |
| ema（窗口 1/5/20） | 误差为 0 |
| pct_change | 误差为 0（改成用 float32 计算之后） |
| correlation、beta（窗口 5/20） | 误差为 0 |
| log | err 1.1e-3（按上面判定公式算出的误差与容差之比，≤ 1 即通过），在 float32 舍入范围内 |
| zscore | err 1.5e-2，max_rel 2.5e-3，原因是 pandas 输入为 float32 |
| 嵌套表达式 / 已选因子 | 38/40 通过 |

**没通过的两个用例**
- 用例 44：`correlation(std(close,10), turnover_rate, 20)`
  - 32 个 NaN 位置不一致；
  - 181 个 inf 与 NaN 互相对不上（约占全部元素的 0.6%）。
- 用例 58：一个已选因子，其中含有 `max(correlation(...))`，1 个 NaN 位置不一致。

**原因**
- 这两个用例都在中间结果 std 上再算 correlation。
- 在 std 几乎不变的窗口里，相关系数的分母接近 0，pandas 自己算出来也是 ±inf 或数值噪声。
- pandas 的中间结果是 float64，我们存成 float32（显存和带宽减半），所以分母是不是恰好为 0 会不一样。

**处理**
- 暂时记为已知差异，不改成 double 存储。
- E6–E8 做完后看了对 RankIC 的影响：用例 44 的日度 IC 最多差 4.4e-4，fitness 差 7.2e-5，候选是否被接受不变（见下一节）。

**调试过程**（报告里可以写成"数值一致性"小节）

| 版本 | 通过数 | 修了什么 |
|---|---|---|
| v1 | 53/88 | 教科书写法：滑动和、滑动方差 |
| v2 | 82/88 | 照 pandas 3.0.3 源码移植：Kahan 求和（加、减分开补偿）、同值序列直接返回原值、Welford 方差 + 数值不稳定时整窗重算、ewm 缺失值时权重衰减 |
| v3 | 86/88 | pct_change 改用 float32；判定条件从纯 rtol 改成 allclose |

教训：
- 舍入上的一点差别，会决定一个窗口算不算"常数"，进而决定 correlation 是 NaN、inf 还是有限值。
- 所以要和原版逐元素对上，必须照抄 pandas 的算法，不能只保证数学上等价。

### 2026-10-31 E6–E8：日度 RankIC 与 fitness vs Python

**实现**（`src/core/metrics.cpp`）
- `rank_rows_pct`：每天对股票排百分位，并列取平均名次，NaN 保持 NaN。目标收益的排名整个数据集只算一次，所有因子共用。
- `daily_rank_ic`：
  - 因子在**全部非 NaN 股票**上排名（目标为 NaN 的股票也参与），然后才按"两边都有值"做配对掩码，和 pandas `corrwith` 的顺序一致；
  - 每天算 Pearson 相关，±inf 记为 NaN；
  - 同时统计 `missing_ratio = 1 − (因子与目标都有值的格子数)/(目标有值的格子数)`。
- `score_factor`：
  - 先按深度 ≤ 3、节点数 ≤ 11 过滤；
  - 然后取有效日 IC 的均值，要求有效天数比例 ≥ 0.8、缺失比例 ≤ 0.2；
  - 按 `np.array_split` 把日度 IC 切成 4 段（前 `T mod 4` 段多 1 天），求段均值的总体标准差和同号比例；
  - `fitness = |IC| − 0.5·段标准差 − 0.0005·max(节点数−3, 0)`，同号比例 < 0.75 时乘 0.25。
- 每天的计算互相独立，OpenMP 按天并行（还没测速度）。

**验证：分三层，把"代码对不对"和"float32 存储的影响"分开**

| 检查 | 输入 | 对比对象 | 结果 |
|---|---|---|---|
| RankIC 代码（`ic_code`） | pandas 的因子值舍入成 float32 | pandas 对同样舍入后的值算出的 IC | 88/88，最大差 8.9e-16 |
| fitness 代码（`fit_code`） | pandas 的日度 IC | Python 的候选统计量 | 88/88，最大差 8.3e-17 |
| 端到端（`e2e`） | C++ 自己的因子值 → RankIC → fitness | Python 的完整结果 | 60/88 完全一致（≤1e-12）；日度 IC 最大差 5.7e-4，fitness 最大差 9.0e-5；**候选是否接受 88/88 一致** |

另外 `tests/test_metrics.cpp` 用手算的小样本检查了：
- 并列排名；
- 完全正序/反序时 IC = ±1；
- 常数截面和不足 2 对有效值时 IC 为 NaN；
- 先排名再掩码；
- array_split 的段长；
- 同号比例不足时乘 0.25；
- 三个拒绝条件。

**端到端为什么有 28 个用例不完全一致**
- 因子值存成 float32 后，原本不同的 float64 值可能被舍入成同一个数，产生新的并列名次。
- 例如 `mean(close,5)` 的 120×300 面板里，float64 下有 190 处并列，舍入成 float32 后变成 436 处。
- 验证方法：在 pandas 里把它自己的因子值先转成 float32 再算 IC，得到的误差和 C++ 一模一样（例如 1.45e-4 对 1.45e-4）。说明差异全部来自存储精度，不是 RankIC 代码的问题。
- 少数用例（44、58、61 等）还叠加了中间结果的 float32 舍入（pandas 里 float64 与 float32 运算得到 float64，我们统一存 float32）。

**调试中修掉的一个 bug**
- 一个已选因子在第 0 天全部取值为 0（常数截面），pandas 返回 NaN，C++ 却给出一个有限值。
- 原因：261 个相同名次求均值时舍入差了 1 ulp，方差变成一个极小的正数，相关系数成了数值噪声。
- 修复：配对后如果因子或目标的值全部相同，直接返回 NaN。

**结论与待定**
- RankIC 和 fitness 的代码与 Python 等价。
- float32 存储带来的 fitness 差异在 1e-4 以下，比候选之间的典型差距小，暂时保留 float32。
- 后面在一整代的真实批量上，再统计 float32 会不会改变候选的排序和入库结果；如果会，再考虑像 pandas 一样按节点区分 float32/float64。
