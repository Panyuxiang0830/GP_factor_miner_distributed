## halo 三种方案（E4）

| 方案 | 对应 | 怎么做 | 状态 |
|---|---|---|---|
| 一次补齐所需历史 | 策略 A，冗余计算（`H0 ≥ max h`） | 每个 rank 多读 `h` 天的原始字段，本地把整棵树算完，不通信（ema 除外） | ✅ |
| 按需获取子树结果 | 策略 B，子树 halo 交换（`H0 = 0`） | 按 DAG 的 level 逐层算；每层算完后把右邻居需要的尾部 `halo_rows` 行打包，用一次 `MPI_Sendrecv` 发过去 | ✅ |
| 冗余存储 + 按需通信 + 结果复用 | 混合（`0 < H0 < max h`） + 缓存 | 每个节点需要的历史 ≤ `H0` 就本地补算，否则交换 | ✅（跨层缓存未做） |

说明：
- 按日期切块时，一个 rank 缺的历史只会在它的左邻居手里。所以策略 B 不会变成"到处要小数据"：每个 level 只有一次批量 Sendrecv。
- 三种方案共用同一个 `H0` 旋钮。计划先做 B，再用 `H0` 扫出 A 和混合方案。

计划的实验：
- 分别用 p = 1、2、4 和 8 个 rank 跑。
- 对每个 p，`H0` 取 0、10、30、60、89。
- 每次记录这几项：
  - 计算时间；
  - 通信时间；
  - 冗余计算的行数；
  - 显存或内存峰值；
  - 分布式结果与 p=1 是否一致。

### 2026-10-31 E6–E8：日度 RankIC 与 fitness vs Python

**实现**（`src/core/metrics.cpp`）
- `rank_rows_pct`：每天对股票排百分位，并列取平均名次，NaN 保持 NaN。目标收益的排名整个数据集只算一次，所有因子共用。
- `daily_rank_ic`：
  - 因子在**全部非 NaN 股票**上排名（目标为 NaN 的股票也参与），然后才按"两边都有值"做配对掩码，和 pandas `corrwith` 的顺序一致；
  - 每天算 Pearson 相关，±inf 记为 NaN；
  - 同时统计 `missing_ratio = 1 − (因子与目标都有值的格子数)/(目标有值的格子数)`。
- `score_factor`：
  - 先按深度 ≤ 3、节点数 ≤ 11 过滤；
  - 然后取有效日 IC 的均值，要求有效天数比例 ≥ 0.8、缺失比例 ≤ 0.2；
  - 按 `np.array_split` 把日度 IC 切成 4 段（前 `T mod 4` 段多 1 天），求段均值的总体标准差和同号比例；
  - `fitness = |IC| − 0.5·段标准差 − 0.0005·max(节点数−3, 0)`，同号比例 < 0.75 时乘 0.25。
- 每天的计算互相独立，OpenMP 按天并行（还没测速度）。

**验证：分三层，把"代码对不对"和"float32 存储的影响"分开**

| 检查 | 输入 | 对比对象 | 结果 |
|---|---|---|---|
| RankIC 代码（`ic_code`） | pandas 的因子值舍入成 float32 | pandas 对同样舍入后的值算出的 IC | 88/88，最大差 8.9e-16 |
| fitness 代码（`fit_code`） | pandas 的日度 IC | Python 的候选统计量 | 88/88，最大差 8.3e-17 |
| 端到端（`e2e`） | C++ 自己的因子值 → RankIC → fitness | Python 的完整结果 | 60/88 完全一致（≤1e-12）；日度 IC 最大差 5.7e-4，fitness 最大差 9.0e-5；**候选是否接受 88/88 一致** |

另外 `tests/test_metrics.cpp` 用手算的小样本检查了：
- 并列排名；
- 完全正序/反序时 IC = ±1；
- 常数截面和不足 2 对有效值时 IC 为 NaN；
- 先排名再掩码；
- array_split 的段长；
- 同号比例不足时乘 0.25；
- 三个拒绝条件。

**端到端为什么有 28 个用例不完全一致**
- 因子值存成 float32 后，原本不同的 float64 值可能被舍入成同一个数，产生新的并列名次。
- 例如 `mean(close,5)` 的 120×300 面板里，float64 下有 190 处并列，舍入成 float32 后变成 436 处。
- 验证方法：在 pandas 里把它自己的因子值先转成 float32 再算 IC，得到的误差和 C++ 一模一样（例如 1.45e-4 对 1.45e-4）。说明差异全部来自存储精度，不是 RankIC 代码的问题。
- 少数用例（44、58、61 等）还叠加了中间结果的 float32 舍入（pandas 里 float64 与 float32 运算得到 float64，我们统一存 float32）。

**调试中修掉的一个 bug**
- 一个已选因子在第 0 天全部取值为 0（常数截面），pandas 返回 NaN，C++ 却给出一个有限值。
- 原因：261 个相同名次求均值时舍入差了 1 ulp，方差变成一个极小的正数，相关系数成了数值噪声。
- 修复：配对后如果因子或目标的值全部相同，直接返回 NaN。

**结论与待定**
- RankIC 和 fitness 的代码与 Python 等价。
- float32 存储带来的 fitness 差异在 1e-4 以下，比候选之间的典型差距小，暂时保留 float32。
- 后面在一整代的真实批量上，再统计 float32 会不会改变候选的排序和入库结果；如果会，再考虑像 pandas 一样按节点区分 float32/float64。

### 2026-10-31 E4：MPI 按日期切块 + 策略 B

**设计**（`src/mpi/distributed.cpp`、`src/core/ema_scan.cpp`）
- **切块**：T 天平均分给 P 个 rank，前 `T mod P` 个 rank 多 1 天。每个 rank 负责全部股票在自己日期块里的值。
- **逐层计算**：按 DAG 的 level 从叶子往上算。每个节点**只算本 rank 自己的日期**，不重复计算。
- **halo 交换**：一层算完后，把这一层里所有 `halo_rows > 0` 的节点的尾部 `halo_rows` 行打包成一条消息，用一次 `MPI_Sendrecv` 发给右邻居，同时从左邻居收自己缺的历史。rank 0 没有左邻居，收 0 行。
- **叶子**（原始字段）不走通信：每个 rank 直接从文件读自己的日期块加前面 `halo_rows` 天。只有算出来的子树才需要交换。
- **ema**：递推依赖全部历史，任何有限的 halo 都不精确，所以用状态传递：
  1. 每个 rank 先在不知道前一块状态的情况下，把本块总结成一个仿射映射（每只股票：第一个观测值、到它为止的衰减、之后的 `y_end = a·y_first + b`、块末权重）；
  2. rank 0 从 (NaN, 1) 开始，把块末状态（y、old_wt）传给下一个 rank，每个 rank 只做 O(N) 的工作，再往后传；
  3. 每个 rank 用收到的状态重算自己的行。
  - 同一层的所有 ema 节点打包成一条消息。
  - 代价：多扫一遍本块数据（第 1 步），链式传递 P−1 跳。
- **RankIC/fitness**：
  - 每个 rank 对自己的日期算目标排名和日度 IC；
  - 把每个因子的可加统计量（4 段各自的 IC 和与有效天数、目标有值格子数、两边都有值格子数）打包，整批因子只做**一次** `MPI_Allreduce`；
  - 每个 rank 得到相同的 fitness。
- **限制**：要求每个日期块 ≥ 最大 halo（当前 59 天），保证 halo 只来自左邻居。T=1461 时最多可开 24 个 rank。

**为配合分布式改了串行代码的两处数值规则**（已确认保留；Python 同步打了补丁；LaTeX 报告里不写这件事）
- 现象：滑动 std 在"窗口内值完全相同"时（例如停牌期间价格不变），Welford 递推留下的舍入残差取决于从哪一天开始累加。串行可能得到 0，分布式得到 3.5e-8，或者反过来。这个残差再进入 correlation 的分母，就变成 NaN 和 ±inf 对不上。pandas 自己也有这个问题：同一段数据从不同的起点算，残差也不同。
- 新规则（数学上都是精确的，而且结果与起点无关）：
  1. 窗口内所有有效值完全相同时，方差直接取 0；
  2. correlation 的分母（两个方差的乘积）恰好为 0 时返回 NaN，不再用残差算出 ±inf。
- 好处：分布式结果在任意 rank 数下都和串行一致（120 天样本 p=2 时 100% 逐位相同）。
- 代价：在这些常数窗口里不再复现 pandas 的残差噪声。

### 2026-11-01 E4：`H0` 旋钮（策略 A / 混合）

**规则**（`src/core/halo_plan.cpp`）
- 从根往叶子倒着算每个节点的 `need`：父节点要读它前面多少天。
  - 父节点只算自己日期时，需要 `own_lookback(父)`；
  - 父节点被冗余多算了 R 天时，需要 `R + own_lookback(父)`。
- 判断：
  - `need ≤ H0`：本节点多算 `need` 天（冗余计算），不通信；
  - `need > H0`：只算自己的日期，`need` 天从左邻居收（halo 交换）。
- 叶子永远从文件读历史。ema 永远走交换，因为提前几天开始递推不精确。
- 所以：
  - `H0 = 0` 就是策略 B，单元测试检查了此时每个节点的 `need` 都等于原来的 `halo_rows`；
  - `H0 ≥ 最大 lookback` 就是策略 A，只有 ema 的输出需要交换；
  - 中间值是混合方案：深层节点累积的历史超过 `H0` 后就改为交换，交换之后它的子节点又只需要少量历史。
- 冗余计算的行数会累积：父节点多算 R 天，子节点就要多准备 R + 窗口长度天。所以 `H0` 实际上是在"多算的行数"和"通信量"之间取舍。
- rank 0 前面没有历史，所有 `need` 截断为 0；其他 rank 截断为 `t0`，即不早于数据的第一天。

**验证 1：88 个表达式**（完整数据，248 个 DAG 节点）
- H0 ∈ {0, 10, 30, 60, 89} × P ∈ {2, 8}，10 种组合全部判定一致：
  - 99.999% 的值和串行逐位相同；
  - 候选接受不一致 0；fitness 最大差 ≤ 1e-9；各 rank 一致。
- 这批表达式需要历史的中间节点很少：H0=0 时 4 个交换；H0=10 时 2 个交换、2 个冗余；H0 ≥ 30 时 0 个交换、4 个冗余。所以看不出几种方案的差别。

- H0=0 和 H0=89 的误差完全相同。说明误差和交换、冗余这两条路径无关，只和"每块从哪天开始滑动求和"有关。
- 对照实验（单机串行，不用 MPI）：把数据起点从第 0 天挪到第 365 天，和从第 0 天开始的结果比较。只比较不含 ema 的 1161 个因子；ema 在股票停牌后会一直沿用最后一个值，记忆无限长，不能这样比。

|---|---|---|

**初步观察**（正式实验时再细测）
- H0=89 把 halo 通信量从 90 MB 降到 7.6 MB，代价是冗余计算 6232 行，相对每 rank 365 天 × 4002 个节点很小，总时间 69 s → 62 s。
- 但两者的计算和 RankIC 时间都远大于通信。单机共享内存上通信很便宜，H0 的影响要在多节点、真正走网络时才明显。

**分析**
- **MPI 比 OpenMP 扩展得好得多。** 同样 32 线程，16×2 比 1×32 快 2.3 倍。OpenMP 的瓶颈在"计算"阶段：8 线程以后几乎不再变快，而且每次启动结果波动很大。RankIC 阶段的 OpenMP 扩展近乎理想（82.8 → 2.8 s，约 30 倍），说明问题不在 OpenMP 本身，而在算子实现：
  - 滑动窗口算子按股票并行，每只股票都要分配几个临时数组，32 个线程同时向同一个分配器申请内存会互相等锁；
  - 逐元素算子（+ − × ÷ log）每个元素只做一两次运算，受内存带宽限制。
  - MPI 的每个进程有自己的分配器和更小的工作集，所以不受影响。
  - 改进方向：每个线程复用自己的临时数组，减少临时内存分配。CUDA 版本也要注意同样的问题。
- **纯 MPI 的效率损失主要来自负载不均，不是通信。** "等待最慢 rank"占总时间 12–28%，halo 和 ema 链加起来只有 1–5%。Karp–Flatt 指标随 P 增大反而下降（0.021 → 0.010），说明不是固定的串行部分在拖后腿。
  - 负载不均的原因：股票池逐年扩大，每天有数据的股票从 2016 年初的 2636 只增加到 2021 年底的 4845 只。按天数平均切块时，靠后的 rank 要处理更多股票：
    - P=2 时，前一块的工作量是后一块的 80%；
    - P=4 时依次为 68%、80%、86%、100%；
    - P=8 时第一块只有最后一块的 62%。
  - 改进方向：按每天有数据的股票数（工作量）而不是天数来切块，即加权切块。
  - 弱扩展效率下降（16 个 rank 时 0.62）也是同一个原因：P 越大，覆盖的年份越靠后，每天的股票越多，RankIC 从 3.8 s 涨到 6.6 s，等待从 0 涨到 3.6 s。
- **H0 在单机上没有影响。** 所有 rank 在同一台机器上，通信走共享内存，halo 只占约 0.5 s，所以冗余计算和交换的取舍体现不出来。H0 的价值要在多节点（走网络）或 GPU（显存与 PCIe 传输）上才能体现，留到 MPI+CUDA 或 NUS 集群上再测。
- halo 时间（约 1 s）远大于 7 MB 数据在共享内存上的传输时间，主要也是在等左邻居算完，同样是负载不均造成的。

**6. 与原 Python 版本对比**（同一批 200 个因子、同一份 float32 面板）

Python 用挖掘器自己的 `_worker_evaluate`（fork 的进程池，每个任务是一个完整表达式：因子值、日度 RankIC、fitness），脚本 `python/scripts/bench_python.py`。C++ 一栏取相同总核数下最快的配置。

| 核数 | Python s | C++ s（配置） | C++ 比 Python 快 |
|---|---|---|---|
| 1 | 941.82 | 174.35（1×1） | 5.4× |
| 8 | 119.40 | 24.76（8×1） | 4.8× |
| 16 | 63.24 | 12.95（16×1） | 4.9× |
| 32 | 35.64 | 6.99（16×2） | 5.1× |

- Python 的扩展几乎是线性的（32 workers 加速 26.4 倍）：表达式之间完全独立，进程之间不需要通信，200 个表达式分给 32 个进程，每个进程约 6 个。
- 但它的单核速度慢 5.4 倍，这个差距在所有核数下基本不变。C++ 的优势来自单核实现（没有 pandas 的中间 DataFrame、DAG 合并了共享子树），而不是并行方式。
- Python 的方式有两个上限：
  - 每个进程都持有全部数据；
  - 并行度不能超过一批里的表达式数，表达式数少时会有进程空闲。
  MPI 按日期切数据，没有这两个限制。

**为什么通常的最优配置是"少量进程 × 多个线程"，而这里反过来**

进程越多，下面几项开销越大；线程之间没有这些开销：
- **halo 的内存和计算。** 每个 rank 都要额外保存并计算自己块前面的历史（最长 60 天）。P=32 时每块只有约 45 天，历史比自己的块还长；在冗余计算（大 H0）下，额外的计算量甚至超过有效计算。线程共享同一份内存，没有 halo。
- **通信次数。** 每层一次 halo 交换、ema 链要传 P−1 跳、最后一次 Allreduce，都随 P 增加。线程之间直接读共享内存。
- **负载均衡。** 日期块在开始时就固定了，块越小，块之间的工作量差别越显眼，慢的 rank 拖住所有人。OpenMP 线程可以动态分配股票或天（`schedule(dynamic)`），先做完的线程去做剩下的。
- **内存占用。** 每个进程有自己的数据副本和历史行；线程共享一份。

所以在一台机器内，线程通常更划算；进程的不可替代之处是能跨机器（每台机器一个或几个 rank，机器内用线程）。本实验里多进程反而更快，是因为当前算子实现的 OpenMP 扩展性差（上面第一条分析），而不是多进程本身更好。把算子的线程问题修好之后，预期最优配置会向"少量 rank × 多线程"移动。

**这和 Python 的 multiprocessing 不同。** Python 版本是每个进程分到不同的因子，每个进程都持有完整数据，各自独立算完整个表达式（共享子树会被不同进程重复计算），结果再 pickle 传回主进程。MPI 版本是：
- 按日期切数据，每个进程只读 1/P 的数据；
- 同一批因子先合并成 DAG，共享子树只算一次；
- 进程之间只交换很小的 halo 和 IC 统计量；
- 可以跨多台机器。

**测量的可靠性**
- 两轮实验（第一轮用 OpenMPI 绑核，第二轮用 taskset），共有的 P ≤ 8 配置结果基本一致。例如 P=2：87.82 / 87.90 s；P=8：24.78 / 24.76 s。
- 第二轮开头，第一轮失败后残留的一个进程（1 rank × 2 线程）同时在跑，往 CSV 里多写了 3 行，已剔除。残留进程只占 2 个线程，加上实验的 ≤ 32 线程仍在配额内；从上面两轮结果一致来看，影响可以忽略。P=1 的 3 次计时里有一次是 491 s（中位数 174.35 s，和第一轮 174.39 s 一致），就是被它干扰的那次。

### 2026-11-01 E4：多跳 halo（支持 32 个 rank）

- 原来每层 halo 只和左邻居做一次 `MPI_Sendrecv`，要求每个块的天数 ≥ 最长的交换历史。
- 现在 rank s 对节点 i 需要的全局日期 [t0_s − need_i, t0_s) 可以跨越左边好几个 rank：每个 rank 算出自己块里每个右侧 rank 需要的行，一层的所有节点打包成每个对象一条消息，用 `MPI_Isend` / `MPI_Irecv` + `MPI_Waitall` 交换。块够长时只和左邻居通信，和原来一样。
- 一致性（200 个因子，`test_mpi_consistency`）：

| P | H0 | 交换节点 | 逐格完全相同 | NaN 不一致 | 候选判定不一致 | fitness 最大差 |
|---|---|---|---|---|---|---|
| 8 | 0 | 29 | 99.9985% | 0 | 0 | 9.8e-7 |
| 24 | 0 | 29 | 99.9984% | 0 | 0 | 1.5e-6 |
| 32 | 0 | 29 | 99.9984% | 2 | 0 | 1.5e-6 |
| 32 | 30 / 89 | 1 | 99.9984% | 2 | 0 | 1.5e-6 |

  P=32 的 2 个 NaN 来自同一个 `log` 节点：它的输入是一个接近 0 的滚动残差，串行版本的残差为正（log ≈ −39），分布式版本从不同的起点开始累加，残差变成负数，log 得 NaN。这是前面 H0 一节里"滚动和的起点不同，Kahan/Welford 残差不同"的同一机制，不是 halo 的错误；候选判定完全一致。

### 2026-11-01 逐算子计时：OpenMP 卡在哪里

`apply_op` 里按算子累计耗时，`gpe_bench --profile` 输出（1 个 rank，200 个因子，每个配置计时 1 次；原始数据 `bench_20261101/op_profile.csv`）：

| 线程 | 计算阶段 s | 各算子之和 s | 差（算子之外）s | correlation | beta | ema | std | 逐元素（+ − × ÷ log abs） |
|---|---|---|---|---|---|---|---|---|
| 1 | 88.7 | 79.8 | 8.9 | 40.8 | 13.3 | 6.7 | 6.2 | 7.6 |
| 4 | 29.9 | 22.9 | 7.0 | 11.9 | 3.8 | 1.8 | 1.8 | 2.2 |
| 8 | 18.7 | 12.4 | 6.3 | 6.2 | 2.0 | 0.9 | 0.9 | 1.5 |
| 16 | 14.6 | 8.3 | 6.3 | 4.2 | 1.7 | 0.6 | 0.5 | 0.8 |
| 32 | 14.0 | 7.7 | 6.3 | 3.8 | 1.8 | 0.6 | 0.4 | 0.6 |

发现：
1. **最大的瓶颈不在算子里。** "计算"阶段里有约 6.3 s 不随线程数变化，32 线程时占计算阶段的 45%。这段是每个节点在算子之前的 `Panel::reset`：用一个线程把一整块 1461 × 5876 的面板清零（752 个节点共约 26 GB），新申请的内存第一次写入还要触发缺页。这是典型的串行部分（Amdahl 定律）。之前猜测的"分配器锁竞争"不是主因。
2. **correlation / beta 在 16 线程之后不再变快**（beta 甚至变慢）。它们每只股票要申请十几个临时数组，这里才是分配器竞争。
3. **逐元素算子在 32 线程时约 0.19 ns/格**，每格读 8 字节、写 4 字节，相当于约 60 GB/s，已经接近内存带宽，继续加线程也没用；要快只能减少读写次数（例如把相邻的逐元素算子合并成一次遍历）。
4. 读数据（load，约 1.6 s）也是单线程的。

### 2026-11-01 OpenMP 改进 1：面板不清零 + 内存池

**第一步：分配面板时不再清零**（`NoInitAllocator`）。每个面板的每一行在被读之前都会被写（算子、读文件或 halo 交换），所以清零是多余的。

| 线程 | 计算阶段：原来 | 不清零 |
|---|---|---|
| 8 | 18.7 | 14.2 |
| 32 | 14.0 | 18.3（变慢） |

32 线程反而变慢：correlation 3.8 → 8.2 s，ema 0.56 → 2.1 s。原因是真正贵的不是 memset，而是新申请的内存第一次写入时的缺页（内核分配物理页并清零）。不清零之后，缺页从单线程的清零挪进了并行的算子；32 个线程同时缺页，在内核里排队。

**第二步：内存池**（`BufferPool`）。节点的面板被释放时，缓冲区放进池子；新节点从池子里拿容量够的最小缓冲区，不再申请新内存。池子由调用方持有，跨 batch 保留，对应 GP 一代接一代地调用引擎；`gpe_bench` 的预热运行把池子填满。

| 线程 | 总时间：原来 → 内存池 | 计算阶段：原来 → 内存池 | 各算子之和 | correlation | beta |
|---|---|---|---|---|---|
| 8 | 31.8 → 25.0 | 18.7 → 13.2 | 12.6 | 6.2 → 6.3 | 2.0 → 2.0 |
| 16 | 22.7 → 14.5 | 14.6 → 7.6 | 7.5 | 4.2 → 3.7 | 1.7 → 1.3 |
| 32 | 19.3 → **8.76** | 14.0 → **4.56** | 4.45 | 3.8 → 2.1 | 1.8 → 0.84 |

- 1 × 32 线程的加速比从 10.9 提高到 19.9；3 次计时在 8.64–8.93 s 之间，之前不同启动之间 16–24 s 的波动也消失了，说明波动来自缺页。
- "计算阶段"和"各算子之和"之间的差几乎没有了（32 线程：4.56 vs 4.45）。
- correlation / beta 在 16 线程之后也能继续变快，说明它们之前"卡住"主要也是缺页，不是分配器竞争。
- 16 × 2 基本不变（6.80 s）：每个 rank 的面板只有 1/16 大小，缺页本来就少。
- 一致性：P=32 的结果与改动前逐位相同（99.9984% 逐格相同，同样 2 个 NaN），说明没有读到未初始化的内存。
- 现在 32 线程下剩下的串行部分主要是读数据（load 1.4 s，占 16%）。

### 2026-11-01 OpenMP 改进 2：滚动算子每个线程复用临时数组

- 原来滚动算子每只股票都要新申请临时数组。correlation 一只股票就要申请约 13 个长度为 T 的 `vector<double>`：x、y、r，mx、my、xy、valid，以及 3 次 roll_mean、1 次 roll_sum、2 次 roll_var 各返回一个新数组。
- 现在滚动函数改成写进调用方给的数组（`assign` 保留容量）。`#pragma omp parallel` 里每个线程只声明一次这些数组，所有股票共用。计算顺序和公式完全不变：对 pandas 参照的 88 个用例输出与改动前逐行相同，P=32 一致性结果逐位相同。

| 线程 | 总时间：内存池 → 复用 | 计算阶段 | correlation | beta | ema |
|---|---|---|---|---|---|
| 8 | 25.03 → 24.96 | 13.15 → 12.94 | 6.33 → 6.25 | 2.03 → 2.00 | 1.00 → 0.98 |
| 16 | 14.51 → 13.70 | 7.64 → 6.77 | 3.72 → 3.23 | 1.31 → 1.04 | 0.57 → 0.53 |
| 32 | 8.76 → **8.03** | 4.56 → **3.79** | 2.11 → 1.73 | 0.84 → 0.58 | 0.36 → 0.28 |

- 收益随线程数增加：8 线程几乎没有（1%），32 线程总时间减少 8%，correlation 减少 18%，beta 减少 31%。线程越多，同时向分配器申请内存的线程越多，竞争越明显。这说明分配器竞争确实存在，只是比缺页小得多。
- 1 × 32 线程的加速比现在是 174.35 / 8.03 = 21.7（最初为 10.9）；16 × 2 为 6.61 s（6.80 → 6.61）。
- 32 线程下剩下的大头：读数据 1.41 s（18%，单线程）、RankIC 2.83 s、算子 3.79 s。
