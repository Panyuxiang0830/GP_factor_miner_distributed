## 1. 背景：评估引擎在做什么

GP（遗传规划）每一代会产生约 1 万个因子表达式，比如：

```
correlation(close, volume, 20)
rank(ts_mean(close, 5)) / std(close, 10)
```

每个表达式都要在 **1461 个交易日 × 5876 只股票** 的数据上算出因子值，再算每日 RankIC 和适应度（fitness）。这部分已经用 C++ 实现（MPI + OpenMP），这里称为**评估引擎**。

引擎先把一批表达式合并成一张 **DAG**（有向无环图）：

- **叶子**是原始字段，比如 `close`、`volume`；
- **中间节点**是算子，比如 `ts_mean(close, 5)`；
- **根**是每个因子的最终值。
- **相同的子表达式只建一个节点、只算一次**（公共子表达式消除）。节点的键是 `(算子, 窗口, 子节点 id)`，见 `include/gpe/dag.hpp` 里的 `table_`。

每个节点的结果是一张**面板**：T × N 的 float32 矩阵。

| 量 | 数值 |
|---|---|
| 一张面板 | 1461 × 5876 × 4 B ≈ **34.3 MB** |
| 一批（一代的子代） | 约 1 万个根，外加去重后的中间节点 |
| 热启动一批 | 约 3 万个根 |

计算是**逐层**进行的（对应 Lecture 12 的 "top down" 建树：每层并行算完，再同步一次），MPI 版本按日期切块，每层算完做一次 halo 交换。

## 2. 要解决的问题

### 问题 1：一批之内，峰值内存太大

现在的释放规则（`src/mpi/distributed.cpp`，在逐层循环里）：

- 每个节点有一个引用计数 `pending[c]`，表示还有几个父节点没算。
- 中间节点在最后一个父节点算完后释放，缓冲区还给内存池 `BufferPool`。
- **根节点不释放**（条件 `!roots.count(c)`），要等所有层算完，才统一算 RankIC。

所以一批有多少个根，就有多少张根面板同时活着：

| 批量 | 根面板总量（所有 rank 加起来） |
|---|---|
| 200 个（目前的 benchmark） | 约 7 GB |
| 1 万个（一代的子代） | 约 **343 GB** |
| 3 万个（热启动） | 约 **1.03 TB** |

再加上同时活着的中间节点，峰值更高。对照硬件：

- Vanda 一个 CPU 节点 512 GB：一万个勉强放得下，三万个放不下；
- Vanda 一块 A40 GPU 48 GB：只能放大约 1400 张面板；
- 按日期切到 P 个 rank 后，每个 rank 只存 1/P，但**总量不变**。

另一个原因是逐层调度：如果某一层很宽（比如几千个节点），这一层的结果要同时存在，等下一层用完才能释放。

### 问题 2：批与批之间、代与代之间，没有任何复用

- Python 的 `ExpressionCache`（`python/src/gp_factor_miner/cache.py`）只缓存**分数**（RankIC、fitness 等），不缓存因子值。
- C++ 引擎在批与批之间只保留空的缓冲区（`BufferPool`），不保留任何计算结果。
- 但 GP 的子代大量继承父代的子树。比如父代是 `ts_mean(close, 5)`，子代是 `rank(ts_mean(close, 5))`，**每一批都要从原始字段重新算一遍** `ts_mean(close, 5)`。
- 分层进化里这个问题更明显：深度 2、3 的提案有 70% 的子节点来自下层的**基因池**（每层最好的 2000 个因子）。基因池的面板如果常驻内存，深度 3 的表达式往往只需要再算 1–2 个算子。
  - 一个基因池：2000 × 34.3 MB ≈ 69 GB；两层加起来约 137 GB。
  - 一个节点放不下这么多（除了面板还有别的内存开销），GPU 更放不下；**但 4 个节点加起来有 2 TB，按日期切块后每个 rank 只存自己那几天**。这就是"缓存必须分布式才放得下"。

### 两个问题的关系

一句话：**内存是有限的，要决定哪些面板留着、哪些释放、按什么顺序算。** 留得多，复用多，算得少，但容易爆内存；留得少，内存安全，但要重算。

## 3. 理论框架：红蓝卵石博弈（Lecture 12，第 32–34 页）

讲义里的红蓝卵石博弈（red-blue pebbling）正好描述这个问题：

- 计算表示成 DAG：顶点是计算，边是数据依赖。
- 快速存储（cache）大小为 M，慢速存储无限大。
- 四条规则：从慢存储读入 cache；从 cache 写回慢存储；只有当所有输入都在 cache 里时才能计算，结果也放在 cache 里；可以从 cache 删掉数据。
- 通信量 = 读入次数 + 写回次数。目标是让它最小。
- 讲义指出：一般情况下求最优的卵石放法是 **NP 困难**的，实际中用针对具体问题的启发式方法。

对应到我们的项目：

| 卵石博弈 | 我们的引擎 |
|---|---|
| DAG 的顶点 | 表达式节点（算子作用在面板上） |
| 快速存储，大小 M | 每个 rank 的内存（CPU 版），或 GPU 显存（CUDA 版） |
| 慢速存储 | 主机内存或磁盘（GPU 版可以把面板溢出到主机），或者"从原始字段重算" |
| 删掉数据 | 释放面板 |
| 读入 / 写回的代价 | 拷贝、读盘，或者重算这个子树的时间 |

报告里可以用这个模型来定义问题，再说明我们的启发式方法和它的取舍。

## 4. 可能的解决方案

由易到难排列。每一条都要保证**结果和不改之前逐位相同**，因为只是调度和缓存变了，算子没变。

### S1. 根节点算完立即规约，然后按引用计数释放（先做这个）

- 根节点算完这一层，就立刻算每日 RankIC，只保留 IC 统计量（每个因子几十个数）。之后它就像普通节点一样：`pending` 归零就释放。
- 注意：一个根也可能是另一个根的子节点，比如 `ts_mean(close,5)` 和 `rank(ts_mean(close,5))` 都是因子。这种情况下要等父节点算完才能释放，所以**不会破坏批内复用**。
- PCA 签名也需要根面板（见 `../pca/task.md`）。接口上要给"根面板就绪"留一个回调，RankIC 和签名都挂在这里。
- 效果：峰值从 O(根的数量) 降到 O(同时活着的中间节点数)。

### S2. 宽层分块计算

- 一层太宽时，每次只算 C 个节点：算完、处理完、释放，再算下一块。
- 取舍：MPI 版每层做一次 halo 交换。分块后消息变多变小，**延迟开销变大**（Lecture 12 第 21–22 页：延迟比带宽改善得慢，消息次数很关键）。所以 C 不能太小。可以把"每块一次 halo 交换"和"每层一次"放在一起比较。
- 进一步的做法：不按层切，而是把 DAG 切成若干**子批**，每个子批内部共享尽量多的节点，子批之间共享尽量少（相当于图划分）。

### S3. 给定内存预算 M 的调度

- 输入：DAG + 预算 M（每个 rank 多少 GB）。输出：计算顺序 + 何时释放。
- 简单启发式：按拓扑序，优先算"能让最多面板马上释放"的节点；内存不够时，优先释放"重算最便宜"的节点（叶子可以随时从文件重读）。
- GPU 版（显存 48 GB）：放不下时有两种选择——溢出到主机内存，或者丢掉以后重算。两者的代价可以实测比较（PCIe 带宽 vs 算子耗时）。

### S4. 跨批、跨代的面板缓存

- 键：节点的规范化键，和 DAG 的 `table_` 用同一套。值：这个 rank 负责的那段日期的面板（含 halo 行）。
- 候选策略：
  - LRU（最近最少使用）；
  - LFU（使用频率最低先淘汰）；
  - 代价感知（类似 GreedyDual：保留价值 = 重算代价 × 使用频率 / 大小。重算代价可以用已有的逐算子计时 `--profile` 估计，比如 `correlation` 比 `+` 贵得多）；
  - 层结束时把基因池**固定**在缓存里（pin），下一层的提案直接命中。
- 分布式的意义：每个 rank 只缓存自己的日期段，节点越多，缓存总容量越大。可以展示"加节点 → 命中率升高 → 每代耗时下降"，甚至超线性加速比。
- 注意 halo：缓存里的面板需要保存够长的历史行，才能给上层的滚动算子用。如果后来的父节点需要更长的 halo，要么补交换，要么不命中。

### S5. 先用轨迹模拟，再写 C++

S4 的策略不需要一开始就写进 C++。先把每一批的表达式和 DAG 节点键记录下来（第 5 节的 D0），用 Python 回放这些轨迹，模拟不同预算和策略下的命中率、节省的计算量（按逐算子耗时加权）。选出最好的一两种，再在 C++ 里实现、实测。

## 5. 要做的实验

### D0. 产生真实批量轨迹（"组织生产"）

- 运行 Python GP（`python/src/gp_factor_miner/hierarchical_engine.py`）。每一批都经过 `evaluate_batch(batch, depth, stage_number, generation_number, phase)`（约第 1047 行），在这里加一个钩子，把 `batch["expressions"]` 连同 (深度, 阶段, 代数, phase) 写成 JSONL。
- 至少需要：深度 1 完整一层，深度 2 和深度 3 各 ≥ 3 代。深度 2、3 依赖下层的基因池，所以前一层要跑完。
- 耗时估计：Python 版在 32 个进程下评估 1 万个因子约 30 分钟（基准：200 个因子 35.6 秒）。一层（热启动 3 万 + 10 代）大约需要半天。GP 支持断点续跑（checkpoint），可以分多个作业跑。
- 如果时间紧，可以先缩小配置（比如种群 2000），流程跑通后再用正式配置。
- **先问我**：原始项目的运行结果里，可能已经存着每代的种群，那样就不用重跑。
- 轨迹文件包含因子表达式，属于研究成果，**只放在 Vanda 的数据目录，不进仓库**。

### D1. 批内内存：峰值与批量的关系

- 批量 B = 1k、2k、5k、10k、30k，分别测：
  - 当前实现；
  - S1（根节点早释放）；
  - S1 + S2（分块，C 取几个值）。
- 记录：峰值 RSS（`/usr/bin/time -v` 或读 `/proc/self/status` 的 VmHWM）、同时活着的面板数的最大值、总耗时。
- 这也满足评分里的"**串行算法随问题规模的运行时间分析**"：画运行时间和内存随 B 变化的曲线，横轴、纵轴都用对数坐标。

### D2. DAG 合并的效果

- 对每一批真实轨迹，统计：原始节点数、合并后的节点数、比值；按算子类型分开统计。

### D3. 跨代复用率

- 第 g 代的节点有多少比例（按键）在第 g−1 代或基因池里出现过？
- 按逐算子耗时加权，算出"如果全部命中，能省多少计算时间"。这是 S4 的收益上限。

### D4. 缓存策略的模拟（S5）

- 用 D0 的轨迹回放。横轴是缓存预算 M（例如每个 rank 1、2、4、8、16 GB），纵轴是命中率和节省的计算时间。
- 比较：LRU、LFU、代价感知、基因池固定。

### D5. 端到端扩展性（需要 ≥ 256 核）

- 选 D4 最好的策略，在 C++ 里实现，然后用几代真实轨迹测每代耗时。
- **强扩展**：同样几代，节点数 1、2、4（Vanda 一个 CPU 节点 72 核，4 个节点 = 288 核），每种配置的 rank × 线程组合参考已有结论（少量进程 × 多线程通常最好）。报告加速比和并行效率，并对比"有缓存"和"无缓存"。
- **弱扩展**：问题规模随节点数增加。可以让批量 B 随节点数成比例增加，或者用合成的日期长度。
- 解释通信的影响：halo 交换次数（分块后会变多）、Allreduce 的耗时。

### D6. GPU 显存（可选，和 CUDA 版一起做）

- 显存 48 GB 时，比较：分块计算；溢出到主机内存；丢掉重算。

### 验证

- 所有方案下，每个因子的 RankIC 和 fitness 要和"无缓存、无分块"的结果**逐位相同**。用 `tests/test_mpi_consistency.cpp` 的方式比较。
- 缓存命中时，要额外检查 halo 行是否足够。可以专门构造需要更长历史的父节点做测试。
- 报告里要说明验证方法；测试用例不要太多，挑有代表性的几个（老师说过："如果有 100 多个测试，为什么？"）。
