## 2. GP 主循环（Python，基本不动）🐍

以下逻辑和现有代码一致，计算量很小，留在 CPU 上：

**每层：**

1. **热启动**：`balanced_stage_proposals` 生成 3 × 10000 个提案，各种根算子的数量均衡。从第 2 层起，子节点有 70% 的概率取自下层基因池。
2. 提案送进评估引擎，通过准入的成为初始种群。

**每一代（重复 10 次）：**

1. **父代池**：按适应度从高到低挑 2000 个，并限制每个原始字段的出现占比（15% → 20% → 30% 逐步放宽）。
2. **选择**：选出 10000 个父代，配成 5000 对。每次有 50% 的概率用锦标赛（抽 3 个取最好），50% 的概率用 ε-lexicase（以 4 个时间段的 IC 为考题）。
3. **交叉和变异**：以 0.7 的概率做同层交叉；变异包括换字段、换算子、换窗口、换子树。得到约 **1 万个孩子**，规范化后去重。
4. ➡️ 孩子批次送进**评估引擎**。
5. **家庭择优**：每个家庭（2 个父母 + 2 个孩子）中，只有通过准入的孩子才参与比较，最后保留适应度最高的 2 个。
6. **移民**：生成新的随机提案，送进**评估引擎**，直到有 10%（1000 个）通过准入。
7. 得到下一代种群。

**层结束**：在档案里取出本层被接纳的记录，按适应度排序，前 2000 个成为基因池 $G_d$。

> 关键依赖：**第 g+1 代的孩子，要等第 g 代全部评估和准入结束后才能生成**（因为要从幸存者里选父母）。所以流水线只能在"**同一代内部**"展开（见第 4 节），代与代之间有一个天然的同步点。

## 3. 评估引擎：一批表达式的完整处理过程

输入：一批表达式（例如 1 万个孩子），引擎内部再切成若干小块，每块 B 个（例如 B = 512）。
输出：每个表达式的 IC 统计、适应度和签名，以及准入决定。

| 步 | 做什么 | 谁 | 📡 MPI 通信 | 为什么交给它 |
|---|---|---|---|---|
| E1 | **解析与规范化**：把表达式变成树；`a+b` 和 `b+a` 视为同一个；退化表达式（`x−x`、`x/x`）直接丢弃 | 🧵 | rank 0 把这批表达式 **Bcast** 给所有 rank | 字符串和树的处理分支多，适合 CPU |
| E2 | **合并成 DAG**：键相同的子树只保留一个；查询子树缓存（基因池面板），命中的直接复用 | 🧵 | — | 需要哈希表查找，适合 CPU |
| E3 | **推算 halo 长度和执行顺序**：$h = (w-1) + \max h_{\text{子}}$，按拓扑顺序排好节点 | 🧵 | — | 递归遍历一棵小树，适合 CPU |
| E4 | **halo 交换**：把本 rank 最后 $h$ 天的数据发给右边的 rank | 🧵 打包 / 拆包 | **Sendrecv**（经 CPU 中转：显存 → 主机内存 → MPI → 主机内存 → 显存） | — |
| E5 | **按 DAG 执行算子**：逐元素算子做融合；滚动算子用滑动窗口；`ema` 先在本地算出仿射变换 $(A, B)$ | 🟩 一个线程负责一只股票 | `ema` 用 **Exscan** 合并 $(A, B)$ | 大量相同的数值运算，适合 GPU |
| E6 | **每日排名 + 每日 IC**：一个 block 负责一天，块内排序、并列取平均、归约求和 | 🟩 | — | 每天的数据都在本 rank，不需要通信 |
| E7 | **IC 汇总**：按全局日期把 IC 分成 4 段，求每段的 (和, 有效天数)，再算缺失率等 | 🟩 局部求和 | **Allreduce**（B × 约 10 个数） | — |
| E8 | **适应度**：IC 均值、4 段 IC 的标准差、同号比例、复杂度惩罚，然后过滤 | 🧵 rank 0 | — | 每个表达式只有几个数，交给 CPU |
| E9 | **签名预处理**：取全局下标是 5 的倍数的日期，复用 E6 已经算好的排名，NaN 填 0.5，按行去均值，得到 $R$ | 🟩 | — | 数据已经在显存里 |
| E10 | **批量幂迭代 × 4**：$u = Rv$ 在本地算；$\|u\|^2$ 和 $v = R^\top u$ 需要跨 rank 求和 | 🟩 | 每轮做 **Allreduce**（$\|u\|^2$ 共 B 个数；$R^\top u$ 共 B × N 个数） | 访存受限，适合 GPU |
| E11 | **得到签名**：$s = Rv$，归一化并固定正负号 | 🟩 | **Gatherv** 到 rank 0（B × 292 个数） | — |
| E12 | **相似度矩阵**：候选对档案 $\lvert\hat S_c \hat S_a^\top\rvert$，候选之间 $\lvert\hat S_c \hat S_c^\top\rvert$；只回传最大值和接近阈值的候选对 | 🟩 rank 0 的 GPU | — | 矩阵乘，适合 GPU |
| E13 | **复核**：相似度落在 0.90 ± 误差界内的，用 double 重新计算 | 🧵 | — | 数量很少，CPU 用 double 更方便 |
| E14 | **顺序准入**：逐个判断"加入 / 替换 / 拒绝"，更新档案 | 🧵 rank 0（单线程） | 新档案的签名留在 rank 0 的显存里 | **必须按顺序做**，是本质上的串行部分 |
| E15 | 把结果交回 Python | 🐍 ← 🧵 | — | — |

**规律总结**：
- 🧵 CPU 做"**想清楚怎么算**"（E1–E3）和"**按顺序做决定**"（E8、E13、E14）；
- 🟩 GPU 做"**大批量地算**"（E5–E7、E9–E12）；
- 📡 MPI 只在**日期段的边界**（halo、Exscan）和**跨日期的求和**（Allreduce）这两类地方出现。

## 4. 流水线：让 CPU 和 GPU 同时工作

一代的约 1 万个孩子切成小块 c1、c2、c3……：

```
时间 ──────────────────────────────────────────────────────────────►

CPU 线程 A (准备):  [E1-E3 c1][E1-E3 c2][E1-E3 c3][E1-E3 c4]
GPU              :            [E5-E12 c1 ██][E5-E12 c2 ██][E5-E12 c3 ██][E5-E12 c4 ██]
CPU 线程 B (准入):                          [E13-14 c1]   [E13-14 c2]   [E13-14 c3]   [E13-14 c4]
                                                                                       │
                                                         本代结束 ── 同步点 ──► 🐍 家庭择优 → 下一代
```

- **线程 A**：为下一块做解析、合并 DAG、推算 halo，让 GPU 一算完就有活干。
- **GPU**：算当前块。
- **线程 B**：对上一块做复核和顺序准入。

于是串行的准入时间被藏在 GPU 的计算时间里。

**一个必须注意的依赖**：第 c2 块的相似度要和"**已经接纳了 c1 的档案**"比较。解决办法有两种：

- **做法 1**：GPU 先拿"旧档案"算 c2 的相似度，CPU 准入 c2 时，只需要**再补算 c2 和 c1 新进档案的那几个因子**之间的相似度。新进的数量很少，由 CPU 算就够了。现有代码在一个块内部也是这样处理的。
- **做法 2**：不做流水线，按顺序执行，作为保底方案。

报告里可以拿两种方式的时间线对比，看流水线到底节省了多少。

## 5. 多个 rank 的视角

```
mpirun -np 4 ...

rank 0：🐍 GP 主循环 + 引擎（负责第 0 段日期）+ 准入 + 档案
rank 1：引擎工作循环（负责第 1 段日期）
rank 2：引擎工作循环（负责第 2 段日期）
rank 3：引擎工作循环（负责第 3 段日期）

每批：rank 0 Bcast 表达式 → 各 rank 并行执行 E1–E11（中间有 Sendrecv / Exscan / Allreduce）
      → Gatherv 签名到 rank 0 → rank 0 执行 E12–E14 → 结果交给 Python
```

**Python 和 C++ 怎么衔接**：
- **课程实验**：用一个纯 C++ 的驱动程序，读取固定的表达式批次（来自 1481 个因子和各层基因池）直接评估。这样可以复现，计时也干净。
- **完整演示**：C++ 引擎编译成 Python 模块（pybind11）。rank 0 的 Python 调用 `engine.evaluate_batch(...)`，其他 rank 运行 `engine.serve()`，等待 rank 0 发来批次。

## 6. 层结束与缓存

- 基因池 $G_1$、$G_2$ 中每个因子的面板**留在显存里**，作为下一层的子树缓存，供 E2 查询使用。
- 内存估算：每个 rank 需要 2000 × 29 MB / p。4 张卡时每张卡约 14.5 GB 一层；两层都放就需要更多 rank，或者把冷门子树放到主机内存（用 LRU 管理）。
- 缓存不改变任何计算结果，只是**省去重复计算**。报告里给出命中率，以及开关缓存前后的耗时对比。

## 8. 总表：每样东西交给谁

| 交给 🟩 GPU | 交给 🧵 CPU（OpenMP） | 留在 🐍 Python |
|---|---|---|
| 算子执行（E5） | 解析、规范化、DAG 合并、缓存查询（E1–E2） | 热启动提案、父代池 |
| 每日排名、IC（E6–E7） | halo 长度与执行顺序（E3） | 锦标赛、ε-lexicase 选择 |
| 签名预处理、幂迭代（E9–E11） | halo 打包、拆包与 MPI 通信（E4） | 交叉、变异、移民 |
| 相似度矩阵（E12） | 适应度、double 复核（E8、E13） | 家庭择优、基因池晋升 |
| 终筛的 IC 和相关矩阵（F1–F3） | **顺序准入**（E14）、终筛贪心（F4） | checkpoint、日志 |

**纯 CPU 的对照版（MPI + OpenMP）**：上表中 🟩 的部分全部改由 🧵 OpenMP 来做，其余不变。两个版本的 MPI 部分是同一套代码。
